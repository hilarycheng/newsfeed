# News Feed

A public, static, read-only mobile news reader. The deployed bundle has no server-side Worker, database binding, web updater, intake endpoint, administrative route, or custom update key. Content is generated locally by the Rust feeder and published as a self-contained HTML reader with small PWA installation/offline assets. No source intake runs in the hosted page.

## Compact deterministic refresh

The existing enabled schedule runs at the user-requested 06:30, 07:00, 12:00 and 17:00 Asia/Hong_Kong daily (updated 2026-10-13; the previous 12:30 run is replaced). Do not create another schedule. The engine makes zero model/API calls. The wrapper only launches the command, reads its compact status, and publishes validated artifacts to the GitHub Pages branch. It must not read/review/rewrite individual articles.

1. Run the compiled Rust `news-feeder` locally. It performs the registered RSS, Steam and CVE intake, then generates `data/feed.json` and public `dist/index.html` plus the five PWA assets.
2. If status is failure or the process exits nonzero, preserve the previous publication. Source success below 70% or fewer than 30 eligible stories remains a failure. Individual source failures are disclosed.
3. On success, verify the result's `sha256` against `dist/index.html` and verify every entry in `artifacts` before copying the six PWA publication files. Keep `data/`, config, and `.sites-runtime/` local. Publishing credentials and schedules are outside this repository.
4. Validate changes using `cargo test --locked`. Browser fixture QA uses `cargo test --locked browser_reader -- --ignored` with local Chrome/Chromium, without Node.js. No tests fetch publisher content.
5. The compact result retains status, itemCount, sourceCount, failureCount, dealCount, cveJSON, modelCalls=0, artifact and sha256. The checksum now identifies the HTML. The former public feed.json, update-plan.json and _headers are not emitted.

### Deterministic limitations

RSS titles and publisher excerpts stay in their original language. No AI translation or summarization is performed. English and Traditional Chinese are accepted; only the verified ifanr source (id `ifanr`, exact `https://www.ifanr.com/feed`, article host `ifanr.com` or `www.ifanr.com`) has the approved raw Simplified Chinese exception. Other Simplified Chinese and Japanese-only entries remain excluded; their sources stay registered. The ifanr exception is implemented/tested but not live: its current republication license is unverified and it is held disabled. Medium and mapped Medium custom domains are excluded. Gaming uses an explicit known PC single-player title allowlist plus exclusion rules across all feeds, so uncertain/new games may be omitted. Major security items use conservative CVE/severity/OSS rules. Normal aggregator links are skipped when their timestamps only identify a discussion; Show HN/Ask HN are labeled as discussion dates. URL and normalized-title dedup cannot guarantee cross-language event deduplication. RSS iThome timestamps lack a timezone. The official article-page date is recovered deterministically; previously verified, date-only items can be retained within72h and expire normally; no dates are invented. For iThome only, the engine reads the official article publication-date field using bounded requests; it never processes article bodies with a model. Verified calendar dates keep date-only precision (Taipei midnight as the conservative 72-hour filter boundary). Unverifiable entries are skipped.

### Official CVE JSON intake

`scripts/cve_json.py` reads the official [CVE List V5](https://github.com/CVEProject/cvelistV5) deltaLog to discover records, using the most recent 72 hours on the first run and an incremental persisted checkpoint thereafter. Each run resolves the official repository main commit via the public GitHub API (no key) and pins deltaLog and individual record downloads to that immutable revision. The official repository README documents daily full baselines, hourly cumulative-since-baseline deltas and approximately 30 days of deltaLog history; this reader uses the bounded log/individual-record path, not either full archive. Fetches are bounded to 2,000 record attempts per run, 12 concurrent requests, 20-second total transfer timeouts (22-second subprocess cap), 40 MB for the log and 2 MB per record. New work stops at 240 seconds; in-flight requests have at most their remaining 22-second cap and any overrun remains pending. A log retention gap or checkpoint regression fails safely for review; the feeder never downloads the full CVE dataset or browses vulnerability/article bodies with a model. Only the record's `datePublished` sets the news date and rolling 72-hour eligibility. Updates, delta discovery times, fetch times and modified timestamps never renew an older vulnerability.

Supported CVE JSON versions are 5.0, 5.1, 5.1.0, 5.1.1, 5.2 and 5.2.0, including optional `packageURL`. Unknown versions are quarantined rather than guessed. Pending records and errors retain their work for later retries, and a discovery checkpoint does not advance until its batch is fully handled. Persistent rejection tombstones remove rejected vulnerabilities and prevent an old record from reappearing. `data/cve-json-state.json` is durable tracked Site source, including checkpoints, cached records, pending work and rejection state; preserve it across checkouts and concurrent updates. It must never be copied into `dist/` or published as a web asset.

The existing strict major-security threshold is unchanged: critical severity / CVSS >= 9, or explicitly evidenced remote code execution or active exploitation, plus a conservative known open-source product/package mapping. Uncertain product names and ambiguous packages are skipped. Public CVE cards expose the original CVSS version, score, source and vector when supplied; missing metrics are not invented. The rating label distinguishes evidence from a numeric rating. Eligible RSS coverage is merged by CVE ID, with related articles linked on the single card, rather than duplicating the vulnerability across the feed. All source text is escaped and article links require HTTPS.

The CVE refresh runs after RSS eligibility selection and before canonical card generation; CVE IDs mentioned by selected RSS reports are also resolved officially, and unknown/future/expired records never borrow the RSS article date. An incomplete or failed CVE refresh now omits all CVE-dependent cards, reports a partial edition, and preserves its durable intake state; retained intake progress supports a later retry. For incomplete bounded batches, continue the same checkout with another refresh attempt rather than discarding its state. Keep the same checkout for those retries. Do not save or deploy a failed edition or discard its local progress; successful completion commits the accumulated state alongside the validated edition. Do not reset pending work or advance a checkpoint to hide failures. `--from-cache` makes no intake network requests. It requires RSS and Steam observations from the last hour, preserves their actual observation timestamps, and omits all CVE cards when CVE state is incomplete or held. Missing or malformed intake fails safely. A successful edition includes a `CVE List V5` source status and compact `cveJSON` counts on stdout. Run the deterministic CVE fixture suite in addition to the existing feeder, Steam and reader checks; do not print individual article or CVE bodies during routine operation. `scripts/verify-feeder.py` checks unique CVE IDs across all cards and excludes the source-only CVE state from public assets. Steam lifecycle history and all existing category, source, language and gaming filters remain unchanged.

### Persistent failed-source handling

Ordinary HTTP, timeout, parse, and blocked-redirect failures are automatically skipped for that edition, with no candidates from that source. They do not require a new user decision. A platform access-review denial is different: stop the attempted process first and confirm it is no longer running. When the denial identifies an exact enabled RSS URL, run `python scripts/hold-source.py '<exact denied URL>'` offline, then `python scripts/source-request-plan.py` and start a fresh `python scripts/run-feeder.py` for the remaining approved inventory. The helper validates exact registry identity, atomically persists the hold, preserves CVE and every other existing hold, and makes no network requests. Already held URLs stay held on future scheduled runs and cannot contribute cached cards. Do not retry the denied URL, use a substitute URL, change access controls, or bypass review. No per-source approval question is needed to omit a failed source under the user’s explicit skip instruction.

If the denied target is unknown, is neither an exact enabled registered RSS URL nor an explicit hostname matching the registered RSS inventory, or the platform denies the whole operation, stop and report the precise blocker; do not assume it is safe to continue. Keep the existing quality gates: at least 70% RSS success (minimum 10), at least 30 valid cards, fresh intake, preserved durable state, deterministic checks, and successful official publication. Never deploy an incomplete/failed edition just to persist a hold; retain the held checkout and report the blocker. Include `python scripts/test-source-holds.py` with the fixture suites.
